## 1. Функции администратора информационно-вычислительной системы

Задание было вводным: требовалось разобрать функции администратора информационно-вычислительной системы, организацию доступа к локальной сети и сети Интернет, а также порядок установки операционных систем и программного обеспечения на серверы и рабочие станции. Работу я выполнял в роли администратора учебной лаборатории.

Сначала подготовил виртуальные машины, на которых затем выполнялись остальные задания практики. В VirtualBox были созданы и настроены четыре машины: `WS-WIN` под управлением Windows 11 Enterprise 25H2, `SRV-WIN` под управлением Windows Server 2025 Standard, а также `SRV-LIN` и `WS-LIN` под управлением Ubuntu 26.04.1 LTS. Для каждой машины заданы ресурсы: объём оперативной памяти, число процессорных ядер и динамический виртуальный диск. Машины распределены по ролям — серверные и клиентские.

Дальше настроил гостевые операционные системы и сетевые параметры. Машины получили адреса в двух сетях: сеть управления `MGMT` `192.168.56.0/24` использовалась для администрирования, а изолированная сеть `LAB-LAN` `192.168.57.0/24` — для клиент-серверных проверок. Адреса назначались по MAC-адресам адаптеров, а не по порядку их добавления, чтобы исключить путаницу при смене типа адаптера.

Вёл учёт тестовых пользователей. На Windows-сервере созданы доменные учётные записи `labuser01`, `labuser02`, `labuser03`, на Linux-машинах — учётная запись администратора `sysadmin` и тестовые пользователи `ivanov`, `petrov`, `sidorov`, разнесённые по группам в зависимости от набора прав.

Управлял файловыми и сетевыми службами: на `SRV-LIN` подготовлены общие каталоги Samba и экспорт NFS, на `SRV-WIN` — общий ресурс Windows и службы домена. Перед каждым существенным изменением создавал снимок виртуальной машины, чтобы иметь точку возврата, и копировал изменяемые файлы конфигурации. Результаты изменений фиксировал в документации: параметры машин, назначенные адреса, учётные записи и выполненные проверки.

Организация доступа к локальной сети строилась по сегментам. Для учебных проверок применялись только адаптеры Host-Only и Internal Network; внешний адаптер NAT подключался временно, только на время загрузки обновлений и установочных файлов. Такой порядок позволил отрабатывать настройки домена, служб сертификации и файловых ресурсов в замкнутом контуре, не затрагивая рабочую сеть учреждения.

## 2. Основы администрирования Microsoft Windows

Задание требовало выполнить администрирование рабочей станции Windows и конфигурирование её программного обеспечения. Работа выполнялась на машине `WS-WIN`.

Машина `WS-WIN` была создана в VirtualBox с установочного образа Windows 11 Enterprise 25H2. При создании заданы 8 ГБ оперативной памяти, 4 процессорных ядра и динамический виртуальный диск объёмом 80 ГБ. Поскольку установочный образ Windows 11 требовал загрузки в режиме UEFI, для машины были включены EFI и виртуальный модуль TPM 2.0.

После установки системы назначил сетевые адреса по MAC-адресам адаптеров: интерфейс сети управления получил адрес `192.168.56.10/24`, интерфейс учебной сети — `192.168.57.110/24`. Адрес DNS-сервера домена `192.168.57.10` задавался после ввода машины в домен `lab.test`.

Проверку системы выполнял штатными средствами PowerShell. Команда:

```powershell
hostname
```

показала сетевое имя компьютера. Команда:

```powershell
winver
```

подтвердила редакцию операционной системы — Windows 11 Enterprise 25H2. Затем проверил сетевые адаптеры:

```powershell
Get-NetAdapter
```

Вывод перечислил сетевые адаптеры машины вместе с их MAC-адресами, по которым выполнялась привязка адресов. Состояние сетевых параметров проверил командой:

```powershell
Get-NetIPConfiguration
```

Она показала назначенные интерфейсам IPv4-адреса. Наконец, проверил состояние служб:

```powershell
Get-Service
```

Список служб с их состояниями подтвердил, что система запущена и базовые службы работают. Эти проверки зафиксировали рабочее состояние станции до выполнения доменных и файловых заданий.

## 3. Администрирование информационных систем и инфраструктура открытых ключей

Задание было связано со службами сертификации Windows Server. Требовалось развернуть корневой удостоверяющий центр, выпустить тестовый сертификат, проверить работу службы и сохранить резервную копию ключей. Работа выполнялась на виртуальной машине `SRV-WIN` под управлением Windows Server 2025 Standard в редакции Server Core, которая уже была контроллером домена `lab.test`. Машина имела адрес `192.168.57.10` в сети `LAB-LAN` и `192.168.56.20` в сети управления `MGMT`.

Начал с установки роли служб сертификации. Для этого выполнил команду:

```powershell
Install-WindowsFeature -Name ADCS-Cert-Authority -IncludeManagementTools
```

Команда завершилась сообщением `role installed`. После этого перешёл к настройке корневого центра сертификации. Первая попытка вызвать конфигурацию с параметром `-ValidityPeriodYears` завершилась ошибкой: PowerShell сообщил, что параметр с таким именем не найден. Ошибка указала на неверное имя параметра. Правильное сочетание — отдельный параметр `-ValidityPeriod` со значением `Years` и параметр `-ValidityPeriodUnits` со значением `10`. Повторный запуск с исправленными параметрами:

```powershell
Install-AdcsCertificationAuthority -CAType EnterpriseRootCA -CACommonName "LAB-CA" `
  -CryptoProviderName "RSA#Microsoft Software Key Storage Provider" `
  -KeyLength 2048 -HashAlgorithmName SHA256 `
  -ValidityPeriod Years -ValidityPeriodUnits 10 -Force
```

Проверка после настройки показала, что служба `CertSvc` находится в состоянии `Running`. Запись реестра `CommonName` в ветке конфигурации удостоверяющего центра имела значение `LAB-CA`. Утилита `certutil` определила тип центра как `0 -- Enterprise Root CA`, то есть корневой центр предприятия. Таким образом, центр сертификации `LAB-CA` с ключом RSA длиной 2048 бит и алгоритмом хеширования SHA256 был развёрнут и запущен. Срок действия собственного сертификата центра задан десятью годами.

Следующим шагом стал выпуск тестового сертификата. Сначала я попытался запросить сертификат по шаблону `WebServer`:

```powershell
Get-Certificate -Template "WebServer" -CertStoreLocation Cert:\CurrentUser\My
```

Запрос завершился ошибкой `CERTSRV_E_TEMPLATE_DENIED`. Она означала, что шаблон не разрешает текущей учётной записи подавать заявку. Для проверки работоспособности центра этого не требовалось, поэтому использовал шаблон `User`:

```powershell
Get-Certificate -Template "User" -CertStoreLocation Cert:\CurrentUser\My
```

Сертификат был выпущен. В выводе указаны субъект `CN=Administrator, CN=Users, DC=lab, DC=test`, отпечаток `F4B545BCBFA8C7E5EC00B2F616F7ED884DDE9F04` и срок действия один год. Этот результат подтвердил, что центр не только запущен, но и выдаёт сертификаты: заявка прошла, ключ выпущен, срок действия отсчитан корректно.

Последним этапом стало резервное копирование ключей центра сертификации. Командлет `Backup-CARoleService` при попытке сохранить резервную копию базы данных возвращал ошибку `Access is denied` (код `0x80070005`) — не хватало прав на каталог базы. Ключи и сертификат при этом сохранить удалось. Для этого использовал штатную утилиту:

```powershell
certutil -backup C:\CA-Backup3
```

Вывод показал, что ключи и сертификат центра сохранены в файл `LAB-CA.p12`, а рядом создан каталог базы. Размер файла составил 2587 байт. Файл `.p12` содержит закрытый ключ и сертификат центра, поэтому его достаточно для восстановления удостоверяющего центра; резерв базы данных остался ограничением прав и на работоспособность сохранённого ключа не повлиял.

Возникшие в ходе работы неисправности и способы их устранения сведены в таблицу 2.

## 4. Домен Windows Server

Задание требовало развернуть Active Directory Domain Services и DNS, создать лес, организационное подразделение и доменные учётные записи, а затем ввести клиентскую рабочую станцию в домен. Использовались две виртуальные машины: `SRV-WIN` под управлением Windows Server 2025 Standard в роли будущего контроллера домена и `WS-WIN` под управлением Windows 11 Enterprise 25H2 в роли клиента. Домен получил имя `lab.test`, имя NetBIOS — `LAB`.

Сначала привёл имена компьютеров в соответствие с принятой схемой. Автоматические имена `WIN-F5DBNRSFHUD` и `DESKTOP-VCV4MVF` были заменены на `SRV-WIN` и `WS-WIN` соответственно. Для этого использовал `Rename-Computer` с последующей перезагрузкой. Перед изменениями были сделаны снимки виртуальных машин, чтобы иметь точку возврата.

Затем установил роли Active Directory Domain Services и DNS:

```powershell
Install-WindowsFeature -Name AD-Domain-Services,DNS -IncludeManagementTools
```

После установки ролей создал лес домена:

```powershell
$dsrm = ConvertTo-SecureString "<DSRM-пароль>" -AsPlainText -Force
Install-ADDSForest -DomainName "lab.test" -DomainNetbiosName "LAB" -InstallDns `
  -SafeModeAdministratorPassword $dsrm -Force -NoRebootOnCompletion
```

При создании леса система вывела два предупреждения. Первое касалось сетевого адаптера, получающего адрес по DHCP, — это был временный NAT-адаптер с адресом `10.0.2.15`, который не имел статического адреса. Второе сообщало, что делегирование DNS для зоны `lab.test` не создаётся, потому что родительская зона отсутствует. Для изолированной учебной среды оба предупреждения были ожидаемы и на работу домена не повлияли.

После повышения роли служба `NTDS` не запустилась автоматически: время последней загрузки системы не изменилось, то есть перезагрузка после повышения не выполнилась. Я перезагрузил контроллер вручную командой `Restart-Computer -Force`. После этого проверка состояния служб показала ожидаемый результат:

```text

```

Дополнительно проверил параметры домена и леса:

```powershell
Get-ADDomain
Get-ADForest
```

Вывод подтвердил: корень DNS — `lab.test`, имя NetBIOS — `LAB`, distinguished name домена — `DC=lab,DC=test`, имя леса — `lab.test`. Домен и лес были созданы корректно.

Дальше создал организационное подразделение `Lab` и трёх доменных пользователей:

```powershell
New-ADOrganizationalUnit -Name "Lab" -Path "DC=lab,DC=test"
New-ADUser -Name labuser01 -SamAccountName labuser01 -UserPrincipalName labuser01@lab.test `
  -Path "OU=Lab,DC=lab,DC=test" -AccountPassword (...) -Enabled $true -PasswordNeverExpires $true
```

Аналогично были созданы `labuser02` и `labuser03`. При первом запуске пользователи оказались в контейнере `CN=Users`, потому что фильтр выборки с вложенными кавычками в PowerShell отработал с ошибкой параметра. Я заменил фильтр на `-LDAPFilter "(sAMAccountName=…)"` и перенёс объекты в подразделение `Lab` командлетом `Move-ADObject`. Итоговое размещение:

```text
CN=labuser01,OU=Lab,DC=lab,DC=test
CN=labuser02,OU=Lab,DC=lab,DC=test
CN=labuser03,OU=Lab,DC=lab,DC=test
```

Все три учётные записи были включены (`Enabled = True`).

Последним этапом стал ввод клиентской станции `WS-WIN` в домен. Сначала назначил на её интерфейс `Ethernet 3` адрес контроллера домена в качестве DNS-сервера:

```powershell
Set-DnsClientServerAddress -InterfaceAlias "Ethernet 3" -ServerAddresses 192.168.57.10
Add-Computer -DomainName "lab.test" -Credential (Get-Credential LAB\Administrator) -Restart -Force
```

После перезагрузки проверил результат. Имя компьютера — `WS-WIN`, домен — `lab.test`, признак членства `PartOfDomain` — `True`. Проверка имени `lab.test` возвращала адреса контроллера, включая адрес `LAB-LAN` `192.168.57.10`, адрес управления `192.168.56.20` и NAT-адрес `10.0.2.15`. На контроллере объект компьютера был зафиксирован как `CN=WS-WIN,CN=Computers,DC=lab,DC=test`. Клиент вошёл в домен и стал разрешаться по имени.

## 5. Принципы работы операционных систем: ресурсы, права и аудит

Задание требовало показать на примере Windows и Linux, как работает общий файловый ресурс, как разграничиваются права и как фиксируется доступ в журнале. Использовались виртуальные машины `SRV-WIN` (Windows Server 2025, Server Core) и `SRV-LIN` (Ubuntu 26.04.1 LTS).

Начал с общего ресурса Windows. На `SRV-WIN` был создан общий ресурс `LabShare` с каталогом `C:\LabShare`. Проверил его параметры и права на двух уровнях — общем доступе SMB и файловой системе NTFS:

```powershell
Get-SmbShare LabShare
Get-SmbShareAccess LabShare
(Get-Acl C:\LabShare).Access
```

Права SMB:

```text
LAB\LabAdmins  Allow  Full
LAB\LabUsers   Allow  Change
```

Права NTFS:

```text
LAB\LabUsers            Modify, Synchronize
LAB\LabAdmins           FullControl
NT AUTHORITY\SYSTEM     FullControl
BUILTIN\Administrators  FullControl
BUILTIN\Users           ReadAndExecute, CreateFiles
```

Совмещение двух уровней дало нужное разграничение: группа `LabAdmins` получила полный доступ, группа `LabUsers` — право изменять содержимое, а обычные локальные пользователи могли только читать и создавать файлы в отведённой области. Такая двухуровневая модель важна, потому что действует более строгое из двух ограничений.

Дальше включил аудит доступа к файловой системе:

```powershell
auditpol /set /subcategory:"File System" /success:enable /failure:enable
auditpol /get /subcategory:"File System"
```

Проверка показала:

```text
Object Access
  File System   Success and Failure
```

На каталог `C:\LabShare` добавил правило аудита SACL: для `Everyone` фиксировались успешные операции `CreateFiles`. Затем выполнил запись в файл `C:\LabShare\audit-test4.txt`. В журнале безопасности появилось событие 4663:

```text
An attempt was made to access an object.
Subject:        LAB\Administrator
Object Name:    C:\LabShare\audit-test4.txt
Accesses:       WriteData (or AddFile)
Process:        powershell.exe
```

Событие подтвердило, что аудит действительно работает: зафиксированы субъект, объект, тип доступа и процесс, инициировавший операцию. Это и есть проверка журналирования, а не просто включённый параметр.

Затем настроил общие ресурсы на Linux через Samba. На `SRV-LIN` созданы три каталога — `public`, `hr` и `finance`. Проверил конфигурацию и права:

```bash
testparm -s
ls -ld /srv/samba/*
getent group smb_public smb_hr smb_finance
```

Конфигурация показала три ресурса с ограничением по группам:

```text
[public]   path=/srv/samba/public   valid users=@smb_public
[hr]       path=/srv/samba/hr       valid users=@smb_hr
[finance]  path=/srv/samba/finance  valid users=@smb_finance
```

Каталоги имели права `drwxrws---` с владельцем `root` и группой соответствующего ресурса. Бит `setgid` (в числовом виде `2770`) означает, что новые файлы в каталоге наследуют группу ресурса, а не основную группу создавшего файл пользователя. Это важно для общего каталога: файл, созданный одним сотрудником, сразу доступен другим членам группы с нужными правами. Состав групп:

```text
smb_public:  ivanov, petrov, sidorov
smb_hr:      ivanov
smb_finance: petrov
```

Таким образом, пользователь `ivanov` имел доступ к общему и кадровому ресурсам, `petrov` — к общему и финансовому, а `sidorov` — только к общему.

В части базовой защиты проверил, что конфигурации `nftables` и `squid` имеют права `640` с владельцем `root`, файл `/etc/shadow` — права `640` с владельцем `root:shadow`, брандмауэр Windows включён на всех трёх профилях (`Domain`, `Private`, `Public`), а доступ по SSH на `SRV-WIN` ограничен группами `administrators`, `openssh users` и `LabUsers`. Эти меры закрывают служебные файлы и конфигурации от постороннего чтения и ограничивают удалённое администрирование.

## 6. Стоимость владения и инвентаризация

Задание требовало изучить методику расчёта затрат на содержание компьютерных систем и рассчитать стоимость оборудования и его модернизации. Расчёт выполнялся для предприятия ООО «СеверСнаб» — оптово-торговой компании с 16 сотрудниками и 16 рабочими местами. Цены брались из публичных карточек поставщиков; они обозначают ценовые ориентиры, а не утверждённую закупку.

Сначала разделил две разные величины: стоимость планируемой замены оборудования и полную стоимость владения за пять лет. Это разные расчёты, и смешивать их нельзя.

Вариант минимальной замены — самое старое рабочее место предприятия, `WS-SALES-03`. Кандидатный системный блок стоит 49 900 ₽ и продаётся без операционной системы. Если существующий монитор можно оставить, это минимальная начальная сумма; новый монитор добавил бы ещё 5 340 ₽. Лицензия на операционную систему, установка, обслуживание и электроэнергия в этот расчёт не входят, поэтому сумма 49 900 ₽ — только цена самого блока.

Сценарий полного аппаратного обновления складывается из трёх частей. Первая — 16 системных блоков и 16 мониторов: `883 840 ₽`. Вторая — набор сетевых, серверных и кабельных позиций: `575 215 ₽`. Третья — печатающая техника и диски сетевого хранилища: одно многофункциональное устройство, два принтера (один сетевой, второй подключаемый локально по USB после проверки драйвера), термопринтер этикеток и два диска NAS — `182 138 ₽`. Сумма:

```text
883 840 + 575 215 + 182 138 = 1 641 193 ₽
```

Это опубликованные ориентиры на новый комплект оборудования, а не цена текущего имущества и не утверждённая смета. Отдельно стоит заметка по кабелю: две бухты Cat5e дают 610 метров, из которых примерно 260 метров останутся запасом.

Полная стоимость владения за пять лет считается по формуле:

```text
TCO₅ = первоначальная закупка + лицензии и подписки + доставка и монтаж
       + электроэнергия + обслуживание и ремонт + трудозатраты
       − подтверждённая остаточная стоимость
```

На момент выполнения работы оставались неизвестными цены лицензий Windows и серверного программного обеспечения, часы работы и тариф электроэнергии, трудозатраты, доставка, монтаж и обслуживание. Поэтому итоговое значение TCO не объявлялось: 1 641 193 ₽ — это частичный сценарий капитальных затрат, а не полная стоимость владения. Такой подход честнее: не подменять полную оценку затрат суммой закупки и не выдавать ценовой ориентир за итог расчёта.

Инвентаризация технических средств в этом задании опиралась на данные инвентаризации предприятия: количество устройств, их размещение по помещениям, возраст и состояние. Виртуальные машины в инвентаризацию физического предприятия не включались, поскольку они являются учебной средой, а не имуществом организации.

## 7. Администрирование Unix (Ubuntu) и служба NFS

Задание требовало установить сервер NFS, настроить клиент, смонтировать сетевой каталог и проверить разграничение доступа. Использовались виртуальные машины `SRV-LIN` (Ubuntu 26.04.1 LTS, адрес `192.168.57.20`) как сервер и `WS-LIN` (Ubuntu 26.04.1 LTS, адрес `192.168.57.120`) как клиент.

Начал с сервера. Установил пакет и подготовил каталог для экспорта:

```bash
sudo apt-get install -y nfs-kernel-server
sudo mkdir -p /srv/nfs/projects
sudo chown sysadmin:sysadmin /srv/nfs/projects
sudo chmod 775 /srv/nfs/projects
```

В файл `/etc/exports` добавил строку экспорта:

```text
/srv/nfs/projects 192.168.57.0/24(rw,sync,no_subtree_check,root_squash)
```

Параметр `rw` разрешает запись, `sync` фиксирует данные до ответа клиенту, `no_subtree_check` отключает лишнюю проверку поддерева, а `root_squash` отображает корневого пользователя в `nobody`. Экспорт применяется командами `sudo exportfs -ra`, после чего служба включается в автозапуск и запускается:

```bash
sudo exportfs -ra
sudo systemctl enable --now nfs-server
sudo exportfs -v
```

Вывод `exportfs -v` показал применённые параметры:

```text
/srv/nfs/projects 192.168.57.0/24(sync,wdelay,hide,no_subtree_check,sec=sys,rw,secure,root_squash,no_all_squash)
```

Служба `nfs-server` находилась в состоянии `active`. Экспорт был ограничен сетью `192.168.57.0/24`, то есть смонтировать каталог могли только узлы учебной сети.

Затем настроил клиент. Установил пакет, создал точку монтирования и выполнил монтирование:

```bash
sudo apt-get install -y nfs-common
sudo mkdir -p /mnt/projects
sudo mount -t nfs -o vers=3 192.168.57.20:/srv/nfs/projects /mnt/projects
```

Первое монтирование, выполненное без указания версии, поднялось как NFSv4 (`vers=4.2`). В этом режиме попытка записи от учётной записи `sysadmin` завершалась ошибкой `Permission denied`. Причина — не задан домен отображения идентификаторов `idmapd`, из-за чего UID пользователя отображался в `nobody`. Затем перешёл на NFSv3, где идентификаторы передаются напрямую. После перемонтирования с параметром `vers=3` запись от `sysadmin` прошла. Проверка:

```bash
mount | grep nfs
df -h /mnt/projects
```

Вывод:

```text
192.168.57.20:/srv/nfs/projects on /mnt/projects type nfs (rw,vers=3,sec=sys,...)
192.168.57.20:/srv/nfs/projects   39G  7.4G   29G  21% /mnt/projects
```

Каталог смонтировался для чтения и записи, доступный объём составил 39 ГБ, из которых занято 7,4 ГБ.

Последний шаг — проверка прав и параметра `root_squash`. От имени `sysadmin` (UID 1000) создал файл `client-test.txt`; он был создан успешно и получил владельца `sysadmin:sysadmin`. Рядом находился файл `server-test.txt`, созданный на стороне сервера и видимый через общий каталог. Попытка записи от корневого пользователя:

```bash
sudo touch /mnt/projects/root-test.txt
```

завершилась ошибкой `Permission denied`. Это ожидаемое поведение: параметр `root_squash` отображает UID 0 в `nobody`, поэтому корневой пользователь клиента не получает привилегий на общем ресурсе. Листинг каталога:

```text
-rw-rw-r-- 1 sysadmin sysadmin 0 client-test.txt
-rw-r--r-- 1 sysadmin sysadmin 0 server-test.txt
```

Результат подтвердил, что разграничение доступа работает: обычный пользователь с нужными правами записывает файлы, корневой пользователь привилегий не получает, а владельцы файлов отображаются корректно. Если бы потребовался именно NFSv4, следовало бы задать единый домен в `/etc/idmapd.conf` на обеих машинах и перезапустить службу `nfs-idmapd`; для учебной проверки достаточно NFSv3.

## 8. Монтаж сетевого оборудования и приёмка в эксплуатацию

Задание было посвящено монтажу коммутационных шнуров, разделке и оконцовке оптического кабеля, работе с кроссами и шкафами, а также приёмке линейно-кабельных сооружений. По этому разделу изучена технология выполнения работ и составлена технологическая карта с критериями контроля, по которым такие работы принимаются.

Изучил технические руководства по монтажу структурированной кабельной системы, оконцеванию кабеля UTP, проверке медной линии и технике безопасности при работе с оптическим волокном.

В конспекте зафиксировал несколько принципиальных правил. Схемы разводки T568A и T568B нельзя смешивать на концах одной линии: на обоих концах одного кабеля должна использоваться одна схема. При оконцевании пары распускают минимально — не более 13 мм. Кабель следует поддерживать аккуратно, не пережимать и маркировать с обоих концов. Проверка wiremap показывает правильность соединений и простые обрывы или замыкания, но не является полной сертификацией линии по длине и частотным характеристикам — для этого нужны полевые измерители с соответствующими тестами.

Отдельно остановился на безопасности при работе с оптикой. Нельзя смотреть в торец волокна: часть излучения невидима для глаза, а лазерное излучение может повредить сетчатку. Для проверки линии применяют подходящий измерительный прибор и средства защиты глаз. Порядок приёмки линейно-кабельных сооружений в эксплуатацию и требования к заземлению изучены как последовательность контрольных проверок.

Перед сдачей этого раздела сверил конспект с требованиями задания и подтвердил действующий статус нормативных документов.

В ходе работы возникали трудности, и каждая из них была разобрана по цепочке «симптом — причина — решение — проверка». Неверное имя параметра командлета при настройке центра сертификации, ограничение шаблона сертификата, ошибка прав при резервировании базы, незапущенная после повышения служба `NTDS`, ошибки фильтров PowerShell и особенность отображения идентификаторов в NFSv4 — все эти случаи были устранены с подтверждением результата. Наибольшую пользу принёс именно разбор таких ошибок: он показал, что настройка службы — это не одна команда, а последовательность изменений с обязательной проверкой каждой.

Основной вывод практики: любое изменение в инфраструктуре считается выполненным только тогда, когда его результат виден в выводе команды, в журнале или в действии пользователя. Запись «доступ настроен» без проверки с клиента ничего не подтверждает. Это правило одинаково работало для домена, общего каталога, аудита и экспорта NFS.

К недостаткам выполненной части можно отнести то, что оценка полной стоимости владения не была доведена до итогового значения из-за отсутствия подтверждённых данных по лицензиям и тарифам.

В качестве предложения по совершенствованию программы практики отмечу следующее: расчёт стоимости владения целесообразно обеспечить заранее подготовленными исходными данными по лицензиям, тарифам электроэнергии и трудозатратам, чтобы доводить оценку до итогового значения, а не останавливаться на частичном сценарии капитальных затрат.
