## 1. Организация работы почтового сервера

Почтовая служба потребовалась для служебной переписки и передачи вложений внутри лабораторного сегмента. Я не ставил задачу заменить ведомственную почту учреждения. Требовалось понять, как устроен обмен по протоколам SMTP и IMAP, какие параметры отвечают за приём, доставку и хранение сообщений и как подтвердить работоспособность службы с клиентского компьютера. Был выбран локальный домен `lab.test`, имя сервера `mail.lab.test` и три тестовые учётные записи.

Для решения задачи я сравнил связку Postfix и Dovecot с другими вариантами. Внешний почтовый сервис снимает с администратора заботы о доступности, но ограничивает контроль над журналами. Microsoft Exchange даёт календарь и тесную интеграцию с каталогом, однако требует лицензий и более мощного сервера. Связка Postfix и Dovecot не имеет лицензионной стоимости, хорошо документирована и позволяет увидеть каждый этап обработки письма. Для учебной задачи последнее качество оказалось решающим: конфигурация читается в текстовом виде, а результат проверки виден в журнале и в почтовом каталоге.

Почтовый сервер разместил на отдельной виртуальной машине VirtualBox `SRV-MAIL-LIN`, чтобы эксперименты с ящиками и ограничениями не затрагивали другие службы. Сетевые параметры лабораторного сегмента приведены в таблице 1.

**Таблица 1 — Сетевые параметры узлов почтовой службы**

| Узел | Операционная система | Роль | Адрес в лабораторном сегменте | Адрес управления |
|---|---|---|---|---|
| `SRV-MAIL-LIN` | Ubuntu Server 26.04.1 LTS | Почтовый сервер (SMTP + IMAP) | `192.168.57.30/24` | `192.168.56.50` |
| `WS-WIN` | Windows | Почтовый клиент | `192.168.57.110/24` | — |

Установку начал с почтовых компонентов из штатного репозитория Ubuntu:

```bash
sudo apt-get install -y postfix dovecot-core dovecot-imapd mailutils
```

Параметры Postfix задавались заранее через debconf: тип конфигурации «Internet Site», почтовое имя `mail.lab.test`. Вместе с пакетами подтянулся `dovecot-sieve` и служебные библиотеки. После установки я проверил версии компонентов, чтобы сверять дальнейшие параметры именно с ними:

```text
mail_version = 3.10.6
2.4.2 (0962ed2104)
```

Postfix сообщил версию 3.10.6, Dovecot — 2.4.2. Это важно, потому что в Dovecot 2.4 часть имён настроек изменилась по сравнению с примерами для версии 2.3, и перенос старой конфигурации «как есть» привёл бы к ошибкам.

Основные параметры Postfix я задал командой `postconf -e`, которая изменяет действующую конфигурацию без ручной правки файла:

```bash
sudo postconf -e 'myhostname = mail.lab.test'
sudo postconf -e 'mydomain = lab.test'
sudo postconf -e 'myorigin = $mydomain'
sudo postconf -e 'inet_interfaces = all'
sudo postconf -e 'inet_protocols = ipv4'
sudo postconf -e 'mydestination = $myhostname, localhost.$mydomain, localhost, $mydomain'
sudo postconf -e 'home_mailbox = Maildir/'
sudo postconf -e 'mynetworks = 127.0.0.0/8, 192.168.57.0/24'
sudo systemctl restart postfix
```

Проверку действующих параметров выполнил командой `postconf -n`. В выводе зафиксированы ключевые значения: `myhostname = mail.lab.test`, `mydomain = lab.test`, `home_mailbox = Maildir/`, `mydestination = $myhostname, localhost.$mydomain, localhost, $mydomain`, `mynetworks = 127.0.0.0/8, 192.168.57.0/24`, `inet_interfaces = all`, `inet_protocols = ipv4`. Строка `smtpd_relay_restrictions = permit_mynetworks permit_sasl_authenticated defer_unauth_destination` оставлена в значении по умолчанию: она разрешает пересылку только доверенным сетям, а для чужого домена возвращает отказ. Полный вывод приведён в приложении А.

Параметр `mynetworks` я задал явно: `127.0.0.0/8, 192.168.57.0/24`. Из-за этого весь лабораторный сегмент считается доверенным, и клиент `WS-WIN` может отправлять почту через сервер без отдельной SMTP-аутентификации. В изолированной сети это допустимо и упрощает настройку клиента, но при переносе в рабочую сеть доверие по адресу следовало бы заменить аутентификацией. Формат `Maildir/` выбран для хранения: каждое сообщение лежит отдельным файлом, что удобно для доставки и резервного копирования.

Dovecot отвечает за доступ к ящикам по IMAP и за раскладку почты в формат Maildir. В Dovecot 2.4 имена настроек другие, поэтому я задал хранилище и аутентификацию в виде:

```text
mail_driver = maildir
mail_path = %{home}/Maildir
mail_inbox_path = %{home}/Maildir
ssl = no
auth_allow_cleartext = yes
auth_mechanisms = plain login
```

Строки `mail_driver`, `mail_path` и `mail_inbox_path` связывают ящик системного пользователя с каталогом `~/Maildir`, что соответствует параметру `home_mailbox` в Postfix. Параметры `ssl = no` и `auth_allow_cleartext = yes` означают передачу пароля и сообщений открытым текстом. Такое решение допустимо только в изолированном лабораторном сегменте, где трафик не выходит наружу; в рабочей системе первым шагом должно стать включение шифрования. Конфигурацию проверил командой `doveconf -n`, которая вернула `CONFIG_OK` без ошибок.

Тестовые ящики создал как системные пользователи с домашними каталогами и каталогом `Maildir/`:

```bash
sudo adduser labuser01
sudo adduser labuser02
sudo adduser labuser03
```

Пароли задавались через `chpasswd` и в журнал не записывались. Использовать имена сотрудников или служебные адреса было нельзя, поэтому все ящики получили нейтральные имена. Состав учётных записей приведён в таблице 2.

**Таблица 2 — Тестовые учётные записи почтового сервера**

| Ящик | Назначение | Способ проверки |
|---|---|---|
| `labuser01@lab.test` | Отправитель тестовых сообщений | аутентификация, отправка, клиент Thunderbird |
| `labuser02@lab.test` | Получатель и владелец контрольного ящика | чтение `Maildir/new/`, проверка по IMAP |

Запись `auth succeeded` подтвердила, что Dovecot принимает учётные данные системного пользователя. Дальше я отправил тестовое сообщение от `labuser01` к `labuser02`. Команда `mail` в неинтерактивной сессии под `runuser` не сработала, поэтому отправку выполнил через `sendmail -t` с явно заданными заголовками. После этого проверил каталог входящих получателя:

В каталоге `/home/labuser02/Maildir/new/` появился файл сообщения размером 418 байт, принадлежащий пользователю `labuser02`. Это прямое подтверждение того, что Postfix доставил письмо локально, а не отправил его на внешний сервер. Права `-rw-------` показывают, что читать сообщение может только владелец ящика.

Доступ по IMAP проверил запросом к порту 143:

```bash
curl -s --user labuser01:<пароль> imap://192.168.57.30/INBOX
```

Сервер ответил списком папок:


Ответ подтвердил, что по адресу `192.168.57.30` слушает IMAP-служба и что ящик `INBOX` доступен. Затем я проверил прослушиваемые порты:

```text

LISTEN 0 100 0.0.0.0:143 ...
```

Порты 25 (SMTP) и 143 (IMAP) находились в состоянии LISTEN. Наличие слушающего порта само по себе не доказывает работоспособность службы, поэтому основным подтверждением стали доставленное сообщение и ответ IMAP.

## 2. Организация работы шлюза доступа в Интернет

Шлюз доступа в Интернет решает три задачи: соединяет лабораторный сегмент с внешней сетью, скрывает внутренние адреса за одним внешним и контролирует, какие соединения разрешены. В отличие от почтового сервера, который обслуживает только свой домен, шлюз видит весь трафик клиентов и поэтому требует особенно аккуратной настройки. Ошибка в правиле фильтрации может либо открыть лишний доступ, либо отрезать администратора от управления.

Виртуальная машина VirtualBox `SRV-GW-LIN` работала под управлением Ubuntu Server 26.04.1 LTS и имела три сетевых интерфейса. Схема лабораторного сегмента показана ниже.

```text
WS-WIN 192.168.57.110  ──►  SRV-GW-LIN enp0s9 192.168.57.1
                                   │
                                   ├─ enp0s3 10.0.2.15 (NAT) ──► Интернет
                                   └─ Squid 3128
```

Интерфейсы распределились так: `enp0s3` подключён к NAT-адаптеру и получил по DHCP адрес `10.0.2.15/24` — это внешний uplink; `enp0s8` относится к сети управления с адресом `192.168.56.60/24`; `enp0s9` смотрит в лабораторный сегмент с адресом `192.168.57.1/24`. Имена интерфейсов я сверил с адресами, поскольку порядок адаптеров в VirtualBox не всегда совпадает с ожидаемым именем внутри гостевой системы. Если перепутать интерфейсы, правила nftables начнут применяться к другому адаптеру, и диагностика затянется.

Клиент `WS-WIN` находился в лабораторном сегменте с адресом `192.168.57.110/24`. Его собственный NAT-адаптер я отключил, поэтому единственный путь наружу проходил через `SRV-GW-LIN`. Это принципиальное условие проверки: если бы у клиента оставался прямой NAT, он мог бы обходить шлюз, и результаты испытаний ничего не доказывали бы.

Прокси-сервер Squid установил из штатного репозитория:

```bash
sudo apt-get install -y squid
squid -v
```

Команда `squid -v` вывела версию `Squid Cache: Version 7.7`, служба перешла в состояние `active`. После установки включил пересылку пакетов между интерфейсами:

```bash
echo 'net.ipv4.ip_forward=1' | sudo tee /etc/sysctl.d/99-router.conf
sudo sysctl --system
```

Параметр записан в файл `/etc/sysctl.d/99-router.conf`, чтобы пережить перезагрузку. Проверка показала `forward=1`, то есть ядро передаёт пакеты между интерфейсами. Сам по себе этот параметр лишь разрешает маршрутизацию; без правил преобразования адресов пакеты из частной сети ушли бы наружу с внутренними адресами и не получили бы ответа.

Фильтрацию и преобразование адресов настроил средствами nftables. Правила размещены в `/etc/nftables.conf`:

```nft
table inet filter {
  chain input {
    type filter hook input priority filter; policy drop;
    ct state established,related accept
    iif lo accept
    ip protocol icmp accept
    tcp dport 22 accept
    tcp dport 3128 accept
  }
  chain forward {
    type filter hook forward priority filter; policy drop;
    ct state established,related accept
    iifname "enp0s9" oifname "enp0s3" accept
  }
}
table ip nat {
  chain postrouting {
    type nat hook postrouting priority srcnat; policy accept;
    ip saddr 192.168.57.0/24 oifname "enp0s3" masquerade
  }
}
```

Правила применил командой `nft -f /etc/nftables.conf`. Цепочка `input` по умолчанию отбрасывает всё, кроме установленных соединений, петлевого интерфейса, ICMP, SSH (порт 22) и порта прокси 3128. Цепочка `forward` разрешает пересылку только из лабораторного сегмента `enp0s9` на внешний интерфейс `enp0s3` и обратный трафик по установленным соединениям. Правило `masquerade` в таблице `nat` подменяет адрес источника для исходящих пакетов сегмента `192.168.57.0/24`, поэтому наружу уходит один внешний адрес шлюза. Полный дамп правил приведён в приложении Б.

Конфигурацию Squid задал в `/etc/squid/squid.conf`:

```text
http_port 3128
visible_hostname srv-gw-lin
acl lablan src 192.168.57.0/24
acl blocked dstdomain .example.com
http_access deny blocked
http_access allow lablan
http_access deny all
```

Список `lablan` описывает лабораторный сегмент, список `blocked` — тестовый запрещённый домен `example.com`. Правило `deny blocked` стоит перед `allow lablan`, поэтому запросы на запрещённый домен отклоняются раньше, чем разрешение для сегмента. Домен `example.com` выбран как нейтральный тестовый пример запрета; в рабочей конфигурации вместо него подставляется перечень ресурсов, которые организация блокирует.

На клиенте `WS-WIN` я отключил прямой NAT-адаптер, задал маршрут по умолчанию через шлюз и прописал DNS-сервер:

```powershell
Disable-NetAdapter -Name "Ethernet" -Confirm:$false
New-NetRoute -DestinationPrefix "0.0.0.0/0" -InterfaceAlias "Ethernet 3" -NextHop 192.168.57.1
Set-DnsClientServerAddress -InterfaceAlias "Ethernet 3" -ServerAddresses 1.1.1.1
```

Проверка адаптеров показала, что `Ethernet` отключён, а `Ethernet 2` и `Ethernet 3` подняты. Маршрут по умолчанию вёл на `192.168.57.1`. Системный прокси был задан на `192.168.57.1:3128`. После этого выполнил проверки, результаты которых сведены в таблицу 5.

**Таблица 5 — Результаты проверки шлюза и прокси**

| Проверка | Результат |
|---|---|
| `ping 192.168.57.1` | 2/2, 0 % потерь |
| `ping 1.1.1.1` через шлюз | 2/2, TTL 254 (один переход) |
| Прямой `curl http://neverssl.com` | `HTTP/1.1 200 OK` |
| `curl -x 192.168.57.1:3128 http://neverssl.com` | `HTTP/1.1 200 OK` |
| `curl -x 192.168.57.1:3128 http://example.com` | `HTTP/1.1 403 Forbidden` |

Проверка `ping 192.168.57.1` подтвердила доступность шлюза из лабораторного сегмента. Ответ `ping 1.1.1.1` с TTL 254 означает, что пакет прошёл ровно один маршрутизатор — сам шлюз, — и вернулся с внешнего адреса. Прямой запрос `curl` к `neverssl.com` вернул `200 OK`, то есть клиент вышел в Интернет через NAT. Тот же сайт через прокси также дал `200 OK`. Запрос к запрещённому `example.com` через прокси вернул `403 Forbidden` с заголовком `Server: squid/7.7` — правило блокировки сработало.

Журнал Squid зафиксировал обе проверки:

```text
192.168.57.110 TCP_MEM_HIT/200 372 HEAD http://neverssl.com/ - HIER_NONE/- text/html
192.168.57.110 TCP_DENIED/403 326 HEAD http://example.com/ - HIER_NONE/- text/html
```

Запись `TCP_MEM_HIT/200` для `neverssl.com` означает успешный ответ прокси, запись `TCP_DENIED/403` для `example.com` — отказ по списку доступа. Кроме того, в журнале видны служебные соединения Windows по методу CONNECT, которые прошли через прокси с кодом 200. Это подтверждает, что прокси обрабатывал и обычный HTTP-трафик, и туннелированные соединения.

При настройке шлюза возникли трудности, которые я устранил. Они сведены в таблицу 6.

**Таблица 6 — Трудности при настройке шлюза и их устранение**

| Симптом | Причина | Решение | Проверка |
|---|---|---|---|
| UFW на шлюзе мешал forwarding | UFW активен, политика forward — drop | `ufw disable`, явные правила nftables с сохранением SSH и 3128 | `nft list ruleset`, SSH не потерян |
| ICMP через шлюз идёт, TCP — таймаут | Checksum offload на адаптерах VirtualBox | `ethtool -K enp0s3 tx off rx off`, `ethtool -K enp0s9 tx off rx off`; на клиенте отключение offload | Прямой `curl` → `200 OK` |
| `curl http://1.1.1.1` — таймаут | `1.1.1.1` не отвечает по HTTP на порту 80 | Проверка на обычных сайтах (`neverssl.com`, `example.com`) | `200 OK` |

Наиболее показательной оказалась ошибка с контрольной суммой: ICMP-пакеты проходили через шлюз, а TCP-соединения зависали. Причиной был аппаратный расчёт контрольных сумм на адаптерах VirtualBox, который давал сбой при пересылке. Отключение offload через `ethtool` на обоих интерфейсах шлюза и на клиенте вернуло TCP-соединения в работу, что подтвердил прямой `curl` с кодом `200 OK`.

Итог по второй главе: шлюз с маршрутизацией, NAT, фильтрацией nftables и прокси Squid настроен, доступ клиента в Интернет проверен, запрет тестового домена подтверждён журналом прокси.

## 3. Инвентаризация технических средств и контроль оборудования после ремонта

Инвентаризация — это сверка наличия техники с данными учёта и документальное оформление результата. Для администратора она важна тем, что без достоверных инвентарных данных невозможно ни планировать закупки, ни принимать технику из ремонта, ни объяснять расхождения при проверке. В качестве объекта учёта использовано предприятие ООО «СеверСнаб» с собственным складом и обычными рабочими процессами. Это позволило отработать порядок на понятной структуре, не привязываясь к чувствительным данным организации.

Я составил комплект из шести бланков и описал порядок заполнения каждого из них. Состав комплекта приведён в таблице 7, а состав полей каждой формы — в приложении В.

**Таблица 7 — Комплект бланков инвентаризации**

| Форма | Назначение |
|---|---|
| Инвентаризационная опись | Перечень объектов: наименование, код, серийный номер, помещение, количество, состояние |
| Акт приёма-передачи | Передача объекта с указанием комплектности и состояния, подписи обеих сторон |
| Акт технического состояния | Комплектность, внешнее состояние, включение, сеть, основная функция, вывод комиссии |
| Дефектный акт | Симптом, условия возникновения, выполненные проверки, предполагаемая причина, решение |
| Журнал учёта оборудования | Каждое событие отдельной строкой: приём, передача, ремонт, списание |
| Ведомость расхождений | Расхождение между учётом и фактом по каждому объекту, причина, объяснение |

При контроле оборудования после ремонта ключевым документом становится акт технического состояния. Для принтера проверяется контрольная страница, для ПК — вход в систему и сеть, для коммутатора — наличие линков. В дефектном акте нельзя писать «не работает» без описания проверки: нужно зафиксировать симптом, условия возникновения, выполненные проверки и предполагаемую причину. Журнал учёта ведётся так, чтобы каждое событие оставалось отдельной строкой, а ошибка исправлялась новой записью, а не удалением старой.

При приёмке оборудования после ремонта в журнал заносятся идентификатор устройства, заявленный дефект, дата и исполнитель, проверенные функции и результат тестовой страницы или сетевой связи.

## Заключение

Учебная практика проходила в отделе информационных технологий ФГКУ «УВО ВНГ России по Омской области» с ________ по ________. Общий объём работы составил 60 часов. За это время я выполнил три раздела задания: настроил почтовый сервер, настроил шлюз доступа в Интернет и подготовил комплект бланков для инвентаризации технических средств.

По первому разделу развернул в виртуальной машине VirtualBox `SRV-MAIL-LIN` связку Postfix 3.10.6 и Dovecot 2.4.2 с локальным доменом `lab.test`, создал три тестовых ящика, настроил SMTP и IMAP и подтвердил доставку сообщений командой `doveadm`, проверкой каталога `Maildir` и запросом IMAP. Клиентскую часть проверил в Thunderbird 161.0 на `WS-WIN`. По второму разделу настроил в виртуальной машине VirtualBox `SRV-GW-LIN` маршрутизацию, преобразование адресов через masquerade, фильтрацию nftables и прокси Squid 7.7. Доступ клиента в Интернет проверил прямым запросом и через прокси, а запрет тестового домена `example.com` подтвердил ответом `403 Forbidden` и записью `TCP_DENIED/403` в журнале Squid. По третьему разделу составил комплект из шести бланков инвентаризации и описал порядок их заполнения при инвентаризации и контроле техники после ремонта.

Основные трудности были связаны с отличиями свежих версий программного обеспечения от распространённых примеров. В Dovecot 2.4 настройка `disable_plaintext_auth` переименована, из-за чего служба сначала не запускалась; замена на `auth_allow_cleartext = yes` решила проблему. Команда `mail` в неинтерактивной сессии не отправляла письмо, и пришлось перейти на `sendmail -t` с явными заголовками. На шлюзе активный UFW с политикой forward drop мешал пересылке, а сбой расчёта контрольных сумм на адаптерах VirtualBox пропускал ICMP, но обрывал TCP-соединения. Оба случая устранены: UFW отключён в пользу явных правил nftables, offload отключён через `ethtool`. Отдельно столкнулся с тем, что ссылка на MSI Thunderbird по старому адресу возвращала 404; актуальную версию взял из списка версий с архивного сервера Mozilla.

Практика закрепила навыки установки и проверки сетевых служб и показала, что в администрировании важна не только работоспособность службы, но и подтверждение результата. По каждой настройке я теперь фиксирую команду, вывод и то, что этот вывод доказывает. Это дисциплинирует и ускоряет поиск ошибок. Наибольшую пользу принесла работа со свежими версиями Postfix и Dovecot: она заставила сверять имена настроек с документацией конкретного выпуска, а не переносить готовые примеры вслепую.

К недостаткам выполненной работы отнесу отсутствие шифрования на почтовом сервере и прокси — оно допустимо в изолированном сегменте, но в рабочей сети должно быть включено первым делом. Предложение по совершенствованию: добавить в программу практики отдельный шаг по включению TLS и проверке сертификатов.

## ПРИЛОЖЕНИЕ В. Комплект бланков инвентаризации

Комплект подготовлен как пустые формы для ручного заполнения. Ниже приведено назначение и состав полей каждой формы.

**В.1. Инвентаризационная опись.** Заполнить: номер, дату, место, состав комиссии. В строках — наименование и модель, код/инвентарный номер, серийный номер, помещение, количество, состояние, примечание. Для отсутствующего объекта ставится прочерк с объяснением. Подписи — после сверки.
