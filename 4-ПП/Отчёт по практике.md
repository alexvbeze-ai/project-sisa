## 1. Защита информации программно-аппаратными средствами

Первая часть практики была посвящена защите информации программно-аппаратными средствами. Работу я выполнял на виртуальных машинах VirtualBox: шлюзе `SRV-GW-LIN` под управлением Ubuntu 26.04.1 LTS и клиентской машине `WS-WIN`. Шлюз имел три сетевых интерфейса: `enp0s3`, подключённый к сети трансляции адресов (NAT); `enp0s8`, через который шло управление (сеть `MGMT`, адрес `192.168.56.60/24`); `enp0s9`, обращённый к сети клиентов `LAB-LAN` (адрес `192.168.57.1/24`). Клиент `WS-WIN` находился в `LAB-LAN` с адресом `192.168.57.110/24`. Для захвата пакетов использовался `tcpdump` на шлюзе, разбор выполнялся в Wireshark на административной машине `ADMIN-WS`.

Задача состояла в том, чтобы настроить межсетевой экран, ограничить доступ к управлению, проверить, что запрет действительно действует, снять и разобрать пакеты, а затем проверить права доступа к конфигурационным файлам.

**Правила nftables**

Основу защиты составил межсетевой экран nftables. Я применил принцип «запрещено всё, что не разрешено»: входящие соединения по умолчанию отбрасываются, а разрешения выдаются точечно. Итоговый набор правил сохранялся в файле `/etc/nftables.conf`; его полный текст приведён в приложении А.

```nft
table inet filter {
  chain input {
    type filter hook input priority filter; policy drop;
    ct state established,related accept
    iif lo accept
    ip protocol icmp accept
    iifname "enp0s8" tcp dport 22 accept
    tcp dport 3128 accept
  }
  chain forward {
    type filter hook forward priority filter; policy drop;
    ct state established,related accept
    iifname "enp0s9" oifname "enp0s3" accept
  }
}
table ip nat {
  chain postrouting {
    type nat hook postrouting priority srcnat; policy accept;
    ip saddr 192.168.57.0/24 oifname "enp0s3" masquerade
  }
}
```

Разберу назначение цепочек. Цепочка `input` защищает сам шлюз: политика `drop` отбрасывает всё, что не разрешено явно. Пропускаются ответы уже установленных соединений, обмен через петлевой интерфейс `lo` и ICMP-сообщения. Удалённое управление по SSH (порт 22) разрешено только с интерфейса `enp0s8`, то есть из сети управления `MGMT`; с `enp0s9` (`LAB-LAN`) SSH закрыт. Порт 3128, на котором работает прокси-сервер Squid, доступен клиентам.

Цепочка `forward` управляет транзитным трафиком. Её политика тоже `drop`, а единственное разрешение пропускает трафик из `LAB-LAN` (`enp0s9`) во внешнюю сеть (`enp0s3`). Всё остальное отбрасывается.

Таблица `ip nat` выполняет трансляцию адресов: для пакетов из подсети `192.168.57.0/24`, уходящих через интерфейс `enp0s3`, применяется `masquerade` — адрес источника заменяется на адрес внешнего интерфейса шлюза. Без этого клиенты с частными адресами не получили бы ответы из внешней сети. Смысл ограничений сведён в таблицу 1.

**Таблица 1 — Назначение правил межсетевого экрана**

| Цепочка | Правило | Что ограничивает |
|---|---|---|
| `input` | `policy drop` | по умолчанию всё входящее на шлюз запрещено |
| `input` | `iifname "enp0s8" tcp dport 22 accept` | SSH на шлюз — только из сети `MGMT` |
| `input` | `tcp dport 3128 accept` | прокси-порт 3128 доступен клиентам |
| `forward` | `policy drop` | транзит по умолчанию запрещён |
| `forward` | `iifname "enp0s9" oifname "enp0s3" accept` | трафик разрешён только из `LAB-LAN` в NAT |
| `nat` | `masquerade` для `192.168.57.0/24` | выход клиентов во внешнюю сеть через шлюз |

**Права на конфигурационные файлы**

После настройки я проверил права доступа к конфигурационным файлам. Команда `chmod 640` оставила чтение и запись владельцу (root), чтение — группе:

```bash
sudo chmod 640 /etc/nftables.conf /etc/squid/squid.conf
ls -l /etc/nftables.conf /etc/squid/squid.conf /etc/shadow
```

Вывод:

```text
-rw-r----- 1 root root   614 /etc/nftables.conf
-rw-r----- 1 root root   180 /etc/squid/squid.conf
-rw-r----- 1 root shadow 946 /etc/shadow
```

После этого конфигурационные файлы недоступны на чтение посторонним пользователям, а файл `/etc/shadow` принадлежит паре `root:shadow`. В выводе, снятом до изменения режима, `nftables.conf` отображался с правами `rwxr-xr-x`, а `squid.conf` — с правами `rw-r--r--`; после команды оба файла получили режим 640.

**Проверка запрета с клиента**

Проверить работу правил нужно было не по файлу, а с точки зрения клиента. С машины `WS-WIN` я выполнил:

```powershell
Test-NetConnection 192.168.57.1 -Port 22 -InformationLevel Quiet
Test-NetConnection 192.168.57.1 -Port 3128 -InformationLevel Quiet
```

Результат:

```text
False
True
```

Порт 22 закрыт — SSH из `LAB-LAN` запрещён. Порт 3128 открыт — прокси доступен. Значение `False` для SSH подтверждает, что правило `input`, разрешающее SSH только на `enp0s8`, действительно применяется.

**Захват и разбор пакетов**

Оставался вопрос, на каком уровне действует запрет. Если бы порт закрывала сама служба, клиент получил бы отказ, а здесь важно было увидеть поведение фильтра. Во время попытки SSH с клиента я запустил на шлюзе захват на интерфейсе `enp0s9` с фильтром по порту 22:

```bash
sudo tcpdump -i enp0s9 -n -w /tmp/ssh-block.pcap 'tcp port 22'
```

Разбор сохранённого файла показал только SYN-пакеты и их повторные отправки:

```text
IP 192.168.57.110.51849 > 192.168.57.1.22: Flags [S], seq 2014434834, win 65535, length 0
IP 192.168.57.110.51849 > 192.168.57.1.22: Flags [S], seq 2014434834, win 65535, length 0
IP 192.168.57.110.51849 > 192.168.57.1.22: Flags [S], seq 2014434834, win 65535, length 0
IP 192.168.57.110.51849 > 192.168.57.1.22: Flags [S], seq 2014434834, win 65535, length 0
```

Ответный SYN-ACK так и не появился: правило `input` отбрасывает пакет до того, как служба SSH может ответить. Клиент повторяет SYN, потому что не получает подтверждения. Это доказывает блокировку на уровне фильтра пакетов, а не отказ приложения. Тот же файл я открыл в Wireshark на `ADMIN-WS` — картина совпала: повторяющиеся SYN без SYN-ACK.

**Журналы**

Работу служб я проверил по журналам. Команда `journalctl -u nftables` показала, что служба запускается без ошибок. В файле `/var/log/squid/access.log` были запросы клиента `192.168.57.110`: для HTTPS-трафика — `TCP_TUNNEL/200`, для домена `example.com` — `TCP_DENIED/403`. Это подтверждает, что прокси пропускает разрешённый трафик и отклоняет запрещённый.

**Проблемы и их разбор**

Два момента потребовали отдельного разбора (таблица 2). Отсутствие подключения SSH с `LAB-LAN` — не ошибка, а ожидаемый результат правила: управление шлюзом разрешено только из `MGMT`. Вторая сложность — `tcpdump` без `sudo` не видел интерфейс; для захвата понадобились права root.

**Таблица 2 — Проблемы при настройке защиты**

| Симптом | Причина | Решение | Проверка |
|---|---|---|---|
| SSH с `LAB-LAN` на шлюз не подключается | правило `input` разрешает порт 22 только на `enp0s8` | управление шлюзом — только через `MGMT` | `Test-NetConnection` → `False` |
| `tcpdump` без `sudo` не видит интерфейс | нужны права root | запуск `sudo tcpdump` | захват создан |

**Маршруты**

Проверку маршрутов я провёл с двух сторон. С `WS-WIN` выполнил трассировку до внешнего адреса:

```text
tracert -d -h 5 -w 1000 1.1.1.1
  1    <1 ms    <1 ms    <1 ms   192.168.57.1
  2    31 ms    31 ms    31 ms   1.1.1.1
```

Маршрут клиента проходит через шлюз `192.168.57.1`, а затем сразу во внешнюю сеть. С `SRV-LIN` я трассировал локальный адрес шлюза:

```text
traceroute -I -n -m 5 192.168.57.1
 1  192.168.57.1  0.275 ms  0.233 ms  0.229 ms
```

Шлюз доступен за один переход — это ожидаемо для узла той же подсети.

Здесь стоит пояснить ключ `-I`. Первая попытка трассировки без него дала `no reply`: `traceroute` по умолчанию шлёт UDP-зонды, а правила шлюза такой трафик отбрасывают. Ключ `-I` переводит `traceroute` в режим ICMP-эхо, который шлюзом разрешён, и маршрут прорисовывается. Кроме того, изначально пакет `traceroute` не был установлен, поэтому сначала потребовалось выполнить `apt-get install -y traceroute`.

Наиболее сложным оказалось отделить «блокировка настроена» от «блокировка подтверждена». Записать правило нетрудно, но убедиться, что оно действует именно на уровне межсетевого экрана, можно только по выводу: `Test-NetConnection` вернул `False` для SSH, а в захвате `tcpdump` видны только SYN-пакеты без SYN-ACK. Второй сложный момент — трассировка: UDP-зонды `traceroute` отбрасывались правилами шлюза, и маршрут прорисовывался только после перехода на ICMP-режим и установки пакета.

Практика закрепила навыки настройки фильтрации пакетов, чтения журналов и захвата трафика, а также умение оформлять результаты проверок в виде протокола. Отдельное внимание потребовал учёт оборудования: реестр вёлся по проектным позициям с указанием их характеристик и статусов.

В качестве предложений: закрепить порядок регулярной сверки позиций реестра с их характеристиками. Это поддерживает учёт в актуальном состоянии и связывает документирование с проверкой.

### Конфигурация межсетевого экрана nftables

Файл `/etc/nftables.conf` (итоговое состояние):

```nft
#!/usr/sbin/nft -f
flush ruleset

table inet filter {
  chain input {
    type filter hook input priority filter; policy drop;
    ct state established,related accept
    iif lo accept
    ip protocol icmp accept
    iifname "enp0s8" tcp dport 22 accept
    tcp dport 3128 accept
  }
  chain forward {
    type filter hook forward priority filter; policy drop;
    ct state established,related accept
    iifname "enp0s9" oifname "enp0s3" accept
  }
}
table ip nat {
  chain postrouting {
    type nat hook postrouting priority srcnat; policy accept;
    ip saddr 192.168.57.0/24 oifname "enp0s3" masquerade
  }
}
```
